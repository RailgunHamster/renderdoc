## 目标
魔改本仓库 RenderDoc，使其能够截帧《无限暖暖》(Infinity Nikki) PC 端。
游戏路径：`C:\Users\Administrator\game\InfinityNikki Launcher\InfinityNikki\X6Game\Binaries\Win64\X6Game-Win64-Shipping.exe`
游戏必须通过 Launcher 启动（启动参数需附加 Launcher 生成的 token）。

### [2026-07-31] 阶段3：测试管线的曲折调试（重要经验）
**遇到困难与解决（SetThreadContext 注入的坑）：**
1. 手写 x64 stub 字节码多次偏移错误（C7 06 imm32 是 6 字节不是 7 字节等）→ 本地 test_stub.exe + 崩溃处理器逐字节验证
2. 被劫持线程的原始栈**太靠近栈顶保护页**：ntdll 的 `movaps [rsp+0x220]` 写进保护页 → AV。→ stub 里 `mov rsp, 自己的远端栈`（0x20000 已提交）
3. **rbp=0 崩溃**：KERNELBASE 用 [rbp+0x77] 链式帧访问，裸 stub 线程 rbp=0 → AV。→ 用 LdrInitializeThunk 做线程初始化 —— 反汇编发现 **LdrInitializeThunk 会在 start 返回后 NtTerminateThread**，且其内部 LdrpInitializeProcess 在已初始化进程上会崩溃（本地测试证实）→ 放弃
4. **真相**：新鲜挂起进程的 LoadLibraryW 在劫持主线程上运行会**静默死亡**（无异常、无WER——加载器直接 NtTerminateProcess）；而 **CreateRemoteThread 路径完全正常**
5. **对照实验结论**：`RENDERDOC_DISABLE_THREADHIJACK=1`（走 CreateRemoteThread 回退）→ 注入+运行+截帧**全部成功**！

**✅ 里程碑：完整截帧管线打通（CreateRemoteThread 路径）**
- rendertestcmd capture → 注入 rendertest.dll → D3D12 hook → API 触发 → **生成 3 个 .rdc 文件（3MB，header 验证 RDOC/1.46/git-hash 正确）**

**当前状态：**
- 劫持路径（SetThreadContext）在新鲜进程上会杀进程 —— 待修复（早期鸟式：原始栈+恢复上下文，或放弃）
- 游戏场景方案选择：优先"游戏自加载代理 DLL"（零跨进程注入），其次 hookIntoChildren，最后 IFEO+helper

## 阶段7：d3d12 代理方案测试（死路）+ 崩溃调查（2026-08-01）

### 本轮成果
1. **app_api.cpp 移植完成**：RENDERTEST_WrapD3D12Device / RENDERTEST_InstallDelayedHooks / RENDERTEST_NotifyHookModule 全部编译成功（dumpbin 验证 4 个导出）。
2. **d3d12.dll 代理构建成功**（19 导出转发 d3d12_real.dll + D3D12CreateDevice 拦截 + WrapDeviceWithRendertest 调进程内 rendertest）。
3. **d3d12 代理首次实测命中**：游戏进程调用 D3D12CreateDevice → 代理 → wrap 成功（wrapped 地址正常）→ marker_d3d12_create 生成（游戏确实调用 D3D12CreateDevice！）→ 但游戏崩溃。
4. **崩溃根因1（已修复）**：rendertest 轮询线程 InstallInlineHooks 无脑 12 字节拷贝 trampoline（inline_hooks.h）patch **游戏目录代理 d3d12.dll**（/O2 优化 C++ 含 RIP 相对指令）→ trampoline 错位 → 内存破坏。修复：InstallInlineHooks 只 patch System32 的 d3d12.dll/D3D12Core.dll（代理 DLL 时跳过）。
5. **崩溃根因2（死路确认）**：实验 A（代理不 wrap 直接返回真实设备）仍崩；实验 C（纯代理无 rendertest 注入）**仍崩** → **d3d12.dll 文件替换本身被 ACE 完整性检查杀**（参考 D:\git\renderdoc 笔记 v3：ACE 扫描并恢复 d3d12.dll 代码完整性，有 d3d12.dll 基准）。**d3d12.dll 代理方案在此游戏上不可行**。已恢复基线（删代理 + 恢复 VERSION.dll 链）。

### 重要新证据（marker 分析）
- **marker_loadlib**：游戏进程 LoadLibrary hook **生效**（记录 d3d11/dxgi/d3d12 加载）。
- **marker_getproc**：游戏 GetProcAddress(**d3d11.dll**, "D3D11CreateDevice") **被记录**（GP hook 生效）→ 游戏确实用 kernel32 GP 获取 D3D11 函数！但 **d3d12 的 GP 调用无记录**（游戏获取 d3d12 函数不走 kernel32 GP——bound import / delay-load / 其他路径）。
- **GP 有记录 ≠ 返回 hook**：Hooked_GetProcAddress 只在 DllHooks 匹配（RegisterLibraryHook 注册后）才返回 hook 函数。**时序假说：游戏 GP(d3d11) 发生在 RegisterHooks 完成前 → match 失败 → 返回真实函数 → 游戏用真实 D3D11CreateDevice**。

### 崩溃栈分析（新构建基线崩溃）
- 游戏 Fatal error：EXCEPTION_ACCESS_VIOLATION writing 0x90c2ffb8，崩溃指令 0x90c3000a（未映射页，疑似 ACE 清理代码区域）。
- 栈：X6Game 深层代码调用 rendertest.dll 两个地址（0xaa12/0xaece）→ dumpbin 解析 = **WrappedVkInstance/WrappingPool 的 dynamic initializer（CRT 静态初始化器）** → **不可能在运行期被调用 → 栈启发式误报/栈损坏**。
- 主要嫌疑（已回滚）：本轮新增 GP hook caller 解析（GetModuleHandleExA FROM_ADDRESS 遍历 PEB 模块链表）——游戏早期模块加载频繁（loader lock 中间态）→ 每次 GP 调用遍历 → 崩溃。已回滚（保留时间戳）。
- 次要嫌疑：DllMain 里 fopen/fprintf（marker_dllmain）——loader lock 下 CRT 文件 I/O。
